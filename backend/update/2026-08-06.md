# Update — 2026-08-06

First real build day. Took the repo from a bare Spring Boot "Hello World" skeleton to a
layered MVC backend with the full data model, a working public feed endpoint, a working
admin review flow, and a local content-loading mechanism that stands in for the (deferred)
AI pipeline.

---

## 1. What was done

- **Dependencies (`pom.xml`)** — added Spring Data JPA, Flyway (core + `flyway-database-postgresql`),
  the PostgreSQL driver, and Lombok. Centralized the overridable versions in `<properties>`
  (`lombok.version`, `flyway.version`, `postgresql.version`) pinned to the versions the Spring
  Boot 3.5.4 BOM resolves. Wired Lombok as an annotation-processor path and excluded it from
  the final jar.
- **Configuration (`application.yml`)** — Postgres datasource (env-overridable), Flyway on,
  JPA `ddl-auto: none` (Flyway owns the schema), plus app settings: `app.media.base-url`,
  `app.feed.page-size`, `app.bootstrap.enabled`.
- **Database schema (`db/migration/V1__init.sql`)** — all five README tables created in one
  migration: `admin_user`, `category`, `prompt_template`, `generation_batch`, `content_item`,
  plus a feed index on `content_item`.
- **Layered MVC codebase** — entities, repositories, services, controllers, and DTOs (map below).
- **Local content loader** — reads `resources/data/initial-content.json` on startup and upserts
  it into Postgres (idempotent). This is the temporary stand-in for the generate → review →
  publish pipeline.
- **Static image serving** — `resources/static/images/` is served directly by Spring; images
  drop in there for now (CDN later).
- **Build verified** — `mvn compile` → BUILD SUCCESS. (App run still pending a running Postgres.)

## 2. Why (decisions & reasoning)

- **Postgres + Flyway from day one** (chosen over no-DB / H2) — we want the production-shaped
  schema early. Flyway owns DDL; JPA never auto-creates tables, so local and prod schemas can't
  drift.
- **JSON manifest as the seed source** — lets us describe images we drop into `resources/`
  without a UI, and the loader turns them into real `PUBLISHED` rows. It's idempotent (categories
  matched by `slug`, items by unique `r2_key`) so restarts don't duplicate data.
- **`url` built from `app.media.base-url` + `r2_key`** — this is the load-bearing indirection.
  Today the base is `http://localhost:9303` and images are local static files; moving to
  Cloudflare R2/CDN later is just uploading the same keys and changing one env var. No code or
  data change.
- **Layered MVC packages** (over package-by-feature) — conventional Spring layout, easy to scan
  by role; requested after review.
- **"seed" renamed to `bootstrap/InitialContentLoader`** — "seed" is jargon; the new name says
  what it does (loads initial content on boot).
- **All 5 entities + repositories now, but controllers/services only where used** — the schema is
  whole, and the frontend will call admin endpoints too, so the data layer is complete. Web/
  service layers are added per feature to avoid dead code.
- **Plain MVC, not reactive/async** — `spring-boot-starter-web` = Tomcat, thread-per-request
  (~200 threads), blocking. Concurrency comes from the thread pool + HikariCP connection pool,
  and the feed sits behind a CDN cache anyway, so the origin is barely hit. Reactive would add
  complexity we don't need.
- **`generate`/`publish` left as stubs** — their bodies need the AI image client and R2/
  watermark/WebP, which are deliberately deferred. Endpoints exist (return 501) so the frontend
  can wire to them.

## 3. What each portion does now

**Web layer — `controller/`**
- `FeedController` — `GET /api/feed?lang=&category=&page=` — public, read-only feed.
- `AdminController` — `/admin/**`:
  - `GET /candidates?status=GENERATED` — review queue (working)
  - `POST /candidates/{id}/approve` · `POST /candidates/{id}/reject` — the human-review gate (working)
  - `POST /generate` · `POST /publish` — **stubs, return 501** (pipeline deferred)
- `HelloController` — `GET /` — trivial liveness string, leftover from the skeleton.

**Business layer — `service/`**
- `FeedService` — queries published items (paged), maps entities → `FeedResponse`, builds each
  image URL from `media.base-url` + `r2Key`.
- `AdminReviewService` — lists candidates by status; approve/reject flip `content_item.status`
  (`GENERATED → APPROVED` / `REJECTED`) inside a transaction; 404 if the id doesn't exist.

**Data access — `repository/`** (Spring Data JPA interfaces)
- `ContentItemRepository` — `findPublished(...)` (feed query), `findByStatusOrderByIdDesc`
  (review queue), `existsByR2Key` (idempotent load).
- `CategoryRepository` — `findBySlug`. `AdminUserRepository` — `findByEmail`.
  `PromptTemplateRepository` — active prompts by category. `GenerationBatchRepository` — plain CRUD.

**Entities — `model/`** (JPA, Lombok getters/setters) — one per table:
`AdminUser`, `Category`, `PromptTemplate`, `GenerationBatch`, `ContentItem`.
`ContentItem` is the heart: `status` lifecycle `GENERATED → APPROVED → PUBLISHED` (/`REJECTED`),
`r2_key`, dimensions, `publish_date`; relations to `Category` and (nullable) `GenerationBatch`.

**API contracts — `dto/`**
- `FeedResponse` (`items[]` + `nextPage`) — matches README §4 exactly (`type` lowercased).
- `CandidateResponse` — one item in the admin review list.

**Startup — `bootstrap/`**
- `InitialContentLoader` — on boot (if `app.bootstrap.enabled=true`), reads the manifest and
  upserts categories + `PUBLISHED` items. Idempotent.
- `InitialContentManifest` — record mirroring the JSON shape.

**Schema — `resources/db/migration/V1__init.sql`** — the five tables + feed index; run by Flyway.

**Content — `resources/`**
- `data/initial-content.json` — seed manifest (2 categories seeded; `items` empty until images arrive).
- `static/images/` — drop images here; served at `/images/...`.

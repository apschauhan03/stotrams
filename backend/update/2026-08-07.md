# Update — 2026-08-07

**PR:** https://github.com/apschauhan03/stotrams/pull/2 (branch `day/2026-08-07` → `main`)

The AI image generation pipeline, built and proven end to end. `POST /admin/generate` went
from a 501 stub to a working endpoint that calls OpenAI, generates images in parallel off
the request thread, writes them to disk, and lands them in the review queue as `GENERATED`.
Verified with real images from `gpt-image-2`.

Also removed the `bootstrap/` package, which the pipeline replaces.

---

## 1. What was done

- **Removed `bootstrap/`** — `InitialContentLoader` + `InitialContentManifest`, plus
  `resources/data/` (the JSON manifest and its README) and the `app.bootstrap.enabled`
  property. Also dropped `ContentItemRepository.existsByR2Key`, which existed only for the
  loader's idempotency check.
- **`V2__seed_categories_and_prompts.sql`** — seeds the two launch categories and one active
  prompt template each. Necessary, not incidental: deleting the loader left nothing that
  creates categories, and `generate` cannot run without a category plus a prompt to read.
- **The generation seam** — `ImageGenerator` interface, `ImageRequest` / `GeneratedImage`
  records, `ImageGenerationException`. One implementation per vendor; nothing else in the
  pipeline knows which vendor is in play.
- **Two providers** — `FakeImageGenerator` (draws a local placeholder PNG, no key, no spend,
  configurable latency and failure rate) and `OpenAiImageGenerator` (real, `gpt-image-2`).
- **`ImageStorage` + `LocalImageStorage`** — writes under `resources/static`, carrying an
  explicit TODO that this must become R2/CDN.
- **`AsyncConfig`** — a bounded 4-thread `imageExecutor`, deliberately separate from Tomcat's
  pool and from the common ForkJoinPool.
- **`GenerationService`** — validates, opens a `generation_batch`, fans out one
  `CompletableFuture` per image onto `imageExecutor`, writes each `content_item` in its own
  transaction, and tallies `cost_usd` when the last image settles.
- **`POST /admin/generate?category=&count=&lang=`** — replaces the 501 stub; returns `202`
  with a batch id immediately.
- **Verified live** (see section 3 for numbers) — including the failure path, deliberately.

## 2. Why (decisions & reasoning)

- **A vendor interface rather than a direct API call.** The provider question stayed open for
  most of the day (Gemini → Bedrock → OpenAI). Putting `ImageGenerator` in first meant the
  whole pipeline could be built and tested while that was undecided, and the final answer cost
  one class. `prompt_template.model` already existed to record which model a prompt targets, so
  provider selection is data, not config — `good-morning` ran on OpenAI while `good-night`
  stayed on `fake`, in the same codebase, at the same time.
- **A fake provider as a first-class component, not a test fixture.** It let us prove fan-out,
  storage, batch bookkeeping, and the review queue with no API key and no spend — and it is the
  only way to test the failure path on demand, since a real provider won't fail to order.
- **Off the request thread, necessarily.** A real image takes ~20s; a batch of 25 is minutes.
  Doing that inline would pin a Tomcat thread and time the caller out. Hence `202` + a batch id,
  with progress observed through `GET /admin/candidates`.
- **Bounded concurrency (4), not unlimited.** Every provider rate-limits and every image costs
  money, so the ceiling is a spend control as much as a performance knob. Explicitly *not*
  virtual threads: unbounded concurrency is the thing being avoided here.
- **One transaction per image, never per batch.** Image 13 failing must not roll back the twelve
  that already succeeded. Proven — see below.
- **`MAX_COUNT = 50`** — a typo in `count` spends real money.
- **API key from the environment only.** The repo is public; a key committed to
  `application.properties` would be scraped within minutes. `application-local.yml` is
  gitignored as the file-based alternative.
- **Generated images gitignored.** Multi-MB runtime output headed for R2 is not source.
- **Kept `category.name_en` / `name_hi`.** Reviewed and deliberately left as-is: two languages
  don't justify a translation table, and the frontend needs them for category tabs. Noted that
  nothing reads them yet.

## 3. What each portion does now

**`service/generation/`**
- `ImageGenerator` — the seam. `providerId()` matches the prefix of `prompt_template.model`.
- `ImageRequest` / `GeneratedImage` — provider-agnostic in and out; `GeneratedImage` carries
  bytes, content type, actual dimensions, and cost.
- `GenerationService` — orchestration. `startBatch()` validates (404 unknown category, 409 no
  active prompt / unknown provider, 400 bad count), saves the batch, fans out, returns. Model
  strings split on the **first** colon only, since vendor model ids contain their own.
- `ImageStorage` / `LocalImageStorage` — key in, bytes on disk. The key is the same string as
  `content_item.r2_key`, assigned once at generation and never changed.
- `provider/FakeImageGenerator` — gradient + text PNG, hue from the prompt hash.
- `provider/OpenAiImageGenerator` — `POST /v1/images/generations`, base64 in the response,
  15s connect / 3min read timeouts, and it surfaces OpenAI's own error message on failure.

**`config/AsyncConfig`** — `imageExecutor`: 4 threads, queue 200, `CallerRunsPolicy`,
graceful shutdown.

**`controller/AdminController`** — `/generate` now live and returning `GenerateResponse`.
`/publish` remains a 501 stub.

**Verified live, on real infrastructure:**

| Check | Result |
|---|---|
| Endpoint returns without blocking | `202` in **0.31s** while generation continued |
| Parallelism is real | 6 fake images, 1.5s each → **3.6s** wall clock (9s serial) |
| Runs off the request thread | started on `nio-9303-exec-1`, finalized on `img-3` |
| **One failure doesn't sink the batch** | 40% failure rate → images 1, 3, 7, 8 failed, **4/8 still landed**, batch finalized cleanly |
| Real generation works | **2/2** from `gpt-image-2` in ~42s, 1024×1536, ~2.8MB each |
| Per-category provider selection | `good-morning` on OpenAI and `good-night` on `fake`, simultaneously |

## 4. Stubbed / deferred

- **No prompt-template API.** Changing a prompt or switching a category's provider currently
  requires raw SQL — that is how OpenAI was enabled today. `PromptTemplate` is annotated
  "editable from the admin panel"; the panel and its endpoints don't exist. First thing tomorrow.
- **`POST /admin/publish`** — still 501. Needs watermark + WebP + R2 upload + status flip.
- **No R2/CDN.** `LocalImageStorage` writes to `resources/static` and carries the TODO. Note it
  works from source but not from a packaged jar — resolved by the move to R2, when nothing
  writes locally at all.
- **No watermark / WebP / resize.** Consequence: images are **~2.8MB**, far too heavy for a
  mobile feed on Indian data, and **1024×1536 (2:3)** rather than the intended 1080×1350 (4:5).
  OpenAI only accepts a fixed set of sizes, so the resize belongs with the watermark step.
- **`cost_usd` records $0** — `app.generation.openai.cost-per-image` is unset by design rather
  than hardcoded to a figure that may be wrong. Set `OPENAI_COST_PER_IMAGE` from the actual
  dashboard number and the tally becomes real.
- **No security on `/admin/**`** — unchanged, and now it spends money. This matters more than
  it did yesterday.
- **No scheduled job** — generation is manual only. The `@Scheduled` daily run will call the
  same `startBatch()`.
- **No admin UI.** Discussed at length (configure prompts, view cost, add/remove content,
  delete from CDN); the endpoints behind it are tomorrow's work.
- `status`/`type`/`language` are still plain strings.

## 5. Open items / next

1. **Prompt-template CRUD endpoints** — agreed as the first task tomorrow. Removes raw SQL
   from the loop and unblocks prompt tuning, which is the main lever on image quality.
2. **Set `OPENAI_COST_PER_IMAGE`** from the real dashboard figure, then judge quality settings
   on cost per *published* image, not per generated one.
3. **The publish step** — watermark + resize to 1080×1350 + WebP. This is what fixes the 2.8MB
   file size; the feed is not shippable without it.
4. **R2 + CDN** — replace `LocalImageStorage`, point `app.media.base-url` at the CDN domain.
   Note that deleting a published image is two operations (delete object + purge edge cache),
   so model "unpublish" (a status flip) separately from object deletion.
5. **Security on `/admin/**`** before anything is deployed.
6. **Admin UI** once the endpoints exist.
